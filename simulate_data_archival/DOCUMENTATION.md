## Project Overview

A table's cost grows with its size even when queries only touch recent rows: indexes
deepen, the cache holds fewer useful pages, VACUUM scans more, and backups/restores take
longer. Archival keeps the hot table proportional to the **active** data. The design
questions are: how to move rows safely, where to put them, and how to get them back.

## Schema (init/)

### `00_exports.sh`

Creates `/var/lib/postgresql/exports`, owned by `postgres` (init scripts run as that
user). It stands in for an object-storage bucket.

### `orders` (hot)

```sql
... ) WITH (fillfactor = 90);
CREATE INDEX ... (created_at), (customer_id, created_at DESC), (status);
```

`fillfactor = 90` leaves 10% free space per page so updates (status changes) can be
**HOT** updates — new row versions on the same page without touching indexes. Four
indexes serve the application's varied queries. `id` is `GENERATED BY DEFAULT` so a
restored row can keep its original id.

### `orders_archive` (cold)

```sql
details TEXT COMPRESSION lz4 NOT NULL,
archived_at TIMESTAMPTZ NOT NULL DEFAULT now()
) WITH (fillfactor = 100, autovacuum_vacuum_insert_scale_factor = 0.5);
CREATE INDEX orders_archive_customer_idx ON orders_archive (customer_id, created_at DESC);
```

- **`fillfactor = 100`** — rows are never updated, so free space per page would be waste.
- **`COMPRESSION lz4`** — values large enough to be TOASTed (rows > ~2 KB) are
  compressed with lz4, which decompresses much faster than the default pglz.
- **`autovacuum_vacuum_insert_scale_factor`** — insert-only tables have no dead tuples,
  but still need vacuum to set the visibility map (for index-only scans) and freeze
  rows; this tunes how often that happens.
- **Two indexes** — the primary key and customer history. Every extra index would only
  cost space on data that's rarely searched.
- **`archived_at`** — when the row left the hot table; useful for retention rules.

### `orders_all` view

`UNION ALL` of both tables with an `archived` flag — a transparent read path for code
that needs full history.

### `seed_orders()` procedure

Truncates both tables and regenerates 400k orders spanning three years (the newest 4k are
`open`/`shipped`, the rest `delivered`). The Go program calls it at startup so every
run is identical.

## Application Code (main.go)

### `archive` — the batched mover

```sql
WITH batch AS (
    SELECT id FROM orders
    WHERE status = 'delivered' AND created_at < now() - interval '1 year'
    ORDER BY id LIMIT 25000
    FOR UPDATE SKIP LOCKED
), moved AS (
    DELETE FROM orders o USING batch b WHERE o.id = b.id RETURNING o.*
)
INSERT INTO orders_archive (...) SELECT ... FROM moved;
```

- **One statement per batch** — the delete and insert commit together. A crash leaves
  each row in exactly one table.
- **Batches** — bounded lock time, WAL bursts and replication lag; the job can pause
  and resume.
- **`FOR UPDATE SKIP LOCKED`** — rows currently locked by application transactions are
  skipped this round instead of making the archiver wait (or deadlock).
- The policy filters on status *and* age: an old order that's still open isn't archived.

### Compaction

`DELETE` leaves dead tuples; `VACUUM` makes the space reusable but doesn't return it.
`VACUUM FULL` rewrites the table compactly (261 MB → 84 MB) but takes an `ACCESS
EXCLUSIVE` lock — in production use `pg_repack` or simply let new rows reuse the space.
A full-table scan becomes ~2.5x faster.

### `bytesPerRow`

Table and index bytes per row for both tables. The archive's rows are somewhat smaller
(full pages) and its index overhead per row is lower (2 indexes instead of 4).

### Retrieval strategies

1. **`orders_all` view** — customer 42's history comes back split between hot and
   archive with no app change.
2. **`findOrder`** — query `orders` first, fall back to `orders_archive`. Recent ids hit on
   the first query; archived ids cost one extra round trip.
3. **`restore`** — `WITH back AS (DELETE FROM orders_archive … RETURNING *) INSERT INTO
   orders …` moves an order back atomically, here with status `disputed`.

### `export` — out of the database

In one transaction:

1. Measure rows and bytes (`pg_column_size`) that qualify (older than two years).
2. `COPY (SELECT * FROM orders_archive WHERE … ORDER BY id) TO PROGRAM 'gzip > file'` —
   executed by the server, streaming through gzip (requires superuser or
   `pg_execute_server_program`).
3. `DELETE` those rows.

If the export fails the transaction rolls back and nothing is deleted. `pg_stat_file`
reports the file size: ~24x smaller than the rows. In production, the next step uploads
the file to object storage and records it in a catalogue.

### Retrieval 4 — cold file

On a pinned connection (temp tables are per session): `CREATE TEMP TABLE cold_orders
(LIKE orders_archive)`, `COPY cold_orders FROM PROGRAM 'gunzip -c file'`, then query.
Hundreds of milliseconds instead of microseconds — appropriate for audits, not for the
application.

## Summary: Pros and Cons

**Pros**

- **Hot table stays small** — faster scans and index lookups, better cache hit rate.
- **Cheaper storage** for data nobody reads daily; files are cheapest.
- **Faster maintenance** — vacuum, backups and restores of the hot table.
- **Explicit retention** — deleting an old export file is trivial.

**Cons**

- **Operational job** — the archiver must run, be monitored, and be safe to resume.
- **Cross-tier queries** — history spans tables or files.
- **Space reclamation** — needs `VACUUM FULL`/`pg_repack` or reuse by new rows.
- **Slow cold access** — by design.

**When to use:** large tables with a natural lifecycle. **When not to:** small tables, or
when old data is queried as often as new — keep it hot (or partition and tier it).
