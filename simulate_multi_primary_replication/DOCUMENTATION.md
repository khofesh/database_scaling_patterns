## Project Overview

With a single primary, all writes funnel through one node. **Multi-primary** lets
every node take writes, which helps multi-region latency and availability — but
introduces a problem single-primary systems never have: two nodes changing the same
row concurrently. This project uses PostgreSQL's built-in **logical replication** in
both directions to demonstrate the topology, the failure mode, and a fix.

---

## Infrastructure (docker-compose.yml)

Two identical services, `node_a` and `node_b`, started with:

| Setting                       | Why                                                                 |
| ----------------------------- | ------------------------------------------------------------------- |
| `wal_level=logical`           | WAL must contain row-level change data for publications.            |
| `track_commit_timestamp=on`   | Lets the subscriber know *when* and *by whom* a local row was last changed, which is needed to detect `update_origin_differs` conflicts. |
| `cluster_name=node_a` / `_b`  | Identifies the node; the schema uses it as a column default.       |
| `NODE_ID` env (1 / 2)         | Read by the init script to give each node its own id sequence.     |

Both mount the same `./init` directory; only `NODE_ID` differs. The data volume is
mounted at `/var/lib/postgresql`, the layout the PostgreSQL 18 image expects.

## Schema (init/01_schema.sh)

Logical replication copies **rows, not DDL**, so each node must create the tables
itself. A shell script (rather than plain SQL) is used so `$NODE_ID` can be
interpolated.

### Conflict avoidance with disjoint identities

```sql
id BIGINT GENERATED BY DEFAULT AS IDENTITY (START WITH ${NODE_ID} INCREMENT BY 10)
```

node_a generates `1, 11, 21…`, node_b `2, 12, 22…`. Concurrent inserts can never
produce the same primary key, so the `insert_exists` conflict — which **stops** the
apply worker until an operator intervenes — cannot happen. `BY DEFAULT` (rather than
`ALWAYS`) lets replicated rows carry their original id. UUIDv7 (`uuidv7()`, new in
PG18) is the other common choice.

### The LWW guard

```sql
IF (NEW.updated_at, NEW.updated_by) < (OLD.updated_at, OLD.updated_by) THEN
    RETURN NULL;   -- skip the stale remote update
END IF;
```

A row-value comparison orders by timestamp, then by node name as a deterministic
tie-breaker — both nodes must make the *same* decision or they still diverge.
Returning `NULL` from a `BEFORE` row trigger silently skips that row's update.

The trigger is created **disabled** so the demo can first show behaviour without any
resolution. Later the program runs `ALTER TABLE accounts ENABLE REPLICA TRIGGER
accounts_lww`: a *replica* trigger fires only when `session_replication_role =
replica`, which is how the logical replication apply worker runs. Local application
writes are unaffected.

### Publication

```sql
CREATE PUBLICATION pub_app FOR TABLE orders, accounts;
```

Each node offers its changes to these tables. Subscriptions are created by the Go
program because they need the peer's hostname and cannot run inside a transaction
block (init scripts are fine with that, but keeping setup in Go makes re-runs clean).

## Application Code (main.go)

### Setup — `subscribe`

```sql
CREATE SUBSCRIPTION sub_from_peer
  CONNECTION 'host=node_b port=5432 dbname=app user=postgres password=postgres'
  PUBLICATION pub_app
  WITH (origin = none, copy_data = false, slot_name = 'from_node_b_to_node_a')
```

- **`origin = none`** — the publisher only sends changes that *originated* on it.
  Without this, a row written on A goes to B, B's publication sends it back to A, and
  so on forever. This option (PG16+) is what makes bidirectional native logical
  replication possible.
- **`copy_data = false`** — both nodes start empty, so no initial sync is needed (and
  an initial copy in both directions would duplicate data).
- An explicit `slot_name` keeps the two slots readable in `pg_replication_slots`.

Before creating subscriptions the program drops old ones (this also drops the remote
slot), truncates tables, and resets conflict stats — so every run starts clean.

### Writing everywhere

Two goroutines (`sync.WaitGroup.Go`, Go 1.25+) insert into `orders` on each node at the
same time. `waitFor` then polls until both nodes have all six rows — replication is
asynchronous, so the program never assumes immediacy. The printed ids show the
interleaved per-node sequences.

### Simulating a partition — `concurrentUpdates`

```sql
ALTER SUBSCRIPTION sub_from_peer DISABLE;   -- on both nodes
UPDATE accounts SET balance = 150 ...       -- node_a, t1
UPDATE accounts SET balance = 80  ...       -- node_b, t2
ALTER SUBSCRIPTION sub_from_peer ENABLE;    -- on both nodes
```

Disabling a subscription stops its apply worker but keeps the replication slot on the
publisher, so changes queue up — exactly like a network partition. Re-enabling
delivers the queued changes. `caughtUp` waits until each subscriber's
`latest_end_lsn` reaches the publisher's `pg_current_wal_lsn()`.

### Divergence and detection

Without the guard, node_a applies node_b's `80` and node_b applies node_a's `150`.
The nodes now disagree permanently, and nothing failed. PostgreSQL 18 *does* notice:

```
LOG:  conflict detected on relation "public.accounts": conflict=update_origin_differs
DETAIL:  Updating the row that was modified locally in transaction 770 ...
```

`printConflictStats` reads `pg_stat_subscription_stats.confl_update_origin_differs`
(new in PG18). The counter is flushed asynchronously, so the function polls briefly.
Detection is not resolution: the built-in policy is always "apply the remote change".

### Resolution — last-writer-wins

With the replica trigger enabled the same scenario converges: node_a receives `80`
(newer, applied) and node_b receives `150` (older, skipped). Both end at `80`.

LWW is simple but **discards** the losing write. That's acceptable for overwrite-style
data (a display name), not for deltas (balance += 50). For those, avoid the conflict
(route each key to a home node), use commutative operations, or merge in the app.

## Summary: Pros and Cons

**Pros**

- **Local writes in every region** — no cross-region round trip for a commit.
- **No failover for writes** — if one node dies, the others are already primaries.
- **Native** — PostgreSQL 16+ supports the topology with `origin = none`.

**Cons**

- **Conflicts** — must be designed out or resolved by policy; default behaviour lets
  nodes diverge silently.
- **Eventual consistency** — a read on node B may not see a write just made on A.
- **Operational burden** — DDL, sequences, and large objects are not replicated;
  `insert_exists`-type conflicts halt replication until fixed by hand.
- **No write scaling** — every node still applies every write.

**When to use:** geo-distributed apps whose data is naturally partitioned by region or
user. **When not to:** workloads needing strong consistency across nodes — use a single
primary with synchronous replication, or a consensus-based NewSQL database.
